## The First Plugin

Now before we go and implement our first plugin, let's quickly lay out the plan:

 * The plugin shall be a derivation that contains the plugin's *source*.
   This is because the Go build system just builds all dependencies from source, and we want to make our plugin a dependency that builds along with the main app.
 * To make the plugin be included, we will need to generate code that references it.
   There are two ways to do that:
   Either we dump the plugin's code inside the main app's module or we put it in an own module and reference that.
   The first approach is very inflexible, because without an own `go.mod`, a plugin cannot reference any third-party lib that is not already referenced in the main app.
   Therefore, we go with the latter approach.

We added the function `lib.pluginMetadata`, which extracts the module's name from a `go.mod` file.
The implementation is somewhat crude in that it doesn't support the full syntactic freedom of that file's format, but it will work with any autogenerated files and plugin authors will be aware of the restriction, so that shouldn't be a problem.

In `buildApp`, we added some code generation.
`GO_MOD_APPEND` creates a `require` directive for each plugin, so that the plugin's Go module is a dependency, and a `replace` directory that tells Go that the plugin's module is to be found at the specified path, which is the `src` directory inside the `outPath` of the plugin.
Now only referencing the plugin in `go.mod` does not suffice, the Go code also references it.
Therefore we generate a `plugin.go` file from the list of plugins that does that.





In our directory, do

{% highlight plain %}
mkdir -p externals/simple-plugin
{% endhighlight %}

Since we do not want to set up multiple repositories on some Git hoster, we'll use the `externals` directory to simulate external repositories.
We will never reference `externals` as if it was a local directory; it will only ever be referenced in Flake inputs.
Remember how we excluded `externals` from the sources in the Flake of our main app?
This means that when building the main app, the content of the `externals` directory isn't available, and thus acts like actual external resources.

`simple-plugin` will be our first plugin.
The plugin will be an own Go module, so navigate to its directory and do once again

{% highlight bash %}
nix run nixpkgs#go mod init "example.com/first-plugin"
{% endhighlight %}

We use `nix-filter` to explicitly exclude the externals from the sources of the main app, and also the `flake.nix` which is something sensible to do.
If we don't exclude `flake.nix`, any change there would trigger a rebuild even if it was unnecessary.
Mind that `nix-filter` doesn't work on `self` so you need to give `./.`.

Now, create the `flake.lock`, check in everything, and run it:

{% highlight bash %}
nix flake update
git add flake.* go.mod main.go
git commit -a -m "initial commit"
nix run
{% endhighlight %}

(Committing is optional, but saves us from a warning that the repository is dirty.)
